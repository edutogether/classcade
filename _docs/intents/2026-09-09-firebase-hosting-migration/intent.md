## 문제

배포가 **화면은 GitHub Pages, 데이터는 Firebase**로 갈라져 있었다. 그 결과:

1. **보안 응답 헤더를 붙일 수 없었다.** GitHub Pages는 응답 헤더를 설정하는 수단이 없다. CSP는
   `index.html`의 `<meta>`로만 둘 수 있었고, `frame-ancestors` 같은 지시어는 meta에서 **무시**되므로
   클릭재킹 방어가 사실상 없었다. `X-Frame-Options`·`X-Content-Type-Options`·`Referrer-Policy`·
   `Permissions-Policy`도 마찬가지로 붙일 자리가 없었다.
2. 주소가 `edutogether.github.io/classcade`라 GitHub 주소가 그대로 드러났고, 다른 앱들과 주소 체계가
   달랐다.

같은 이유로 같은 날 Voice Cinema도 Pages를 폐지했으므로, 이 저장소만 남기면 기준이 어긋난다.

## 원하는 결과

- `https://classcade.edutogether.kr`로 접속하면 앱이 뜬다.
- 그 응답에 보안 헤더 5종이 **실제로 실려온다**: CSP, `X-Frame-Options`, `X-Content-Type-Options`,
  `Referrer-Policy`, `Permissions-Policy`. CSP에는 meta로는 불가능했던 `frame-ancestors 'none'`이 들어간다.
- **화면과 기능은 이전 전과 동일하다.** 이건 이전 작업이지 개선 작업이 아니다.
- 옛 주소는 최종적으로 내려간다(단, 새 주소가 검증되기 전까지는 살려둔다).

## 영향받는 사용자·시스템

- **실사용 교사**: 이 앱은 전시·시연이 아니라 상시 서비스다. 이전 중 화면이 달라지거나 기능이
  멈추면 실사용자가 바로 겪는다.
- **경로 체계**: Pages는 `/classcade/` 하위, Firebase는 **루트**다. 경로 접두가 코드에 박혀 있으면
  자산·링크가 전부 깨진다. 이게 이 작업의 최대 리스크였다.
- **Firebase 콘솔**: App Check(reCAPTCHA)와 Auth의 **승인 도메인**에 새 도메인이 없으면, Firestore가
  Enforced 상태라 요청을 경고 없이 **거부**한다.
- **포털 카드 링크**(다른 저장소): 이 세션 범위 밖이라 팀장이 Portal 세션에 별도로 지시했다.

## 제약

협상 대상이 아니었던 것들:

- **UI·기능을 바꾸지 않는다.** 이전이 목적이다.
- **새 주소가 검증되기 전에는 GitHub Pages를 끄지 않는다.** 옛 주소가 살아 있어야 한다.
- **자격증명을 새로 만들거나 저장하지 않는다**(COMMON_STANDARDS §9). 이미 있는 것만 쓴다.
- **커스텀 도메인 연결은 콘솔 작업이라 대표님이 직접 한다.** 세션이 하지 않는다.
- **페어링 서브시스템 코드는 건드리지 않는다**(LOCKED).
- 임시방편으로 넘기지 않는다(§15). 검증 수단이 없으면 없다고 보고한다.

## 미결 질문 (착수 시점에 답을 몰랐던 것 — 아래 "결과"에 답을 적었다)

1. 경로 접두 `/classcade`가 코드 어딘가에 박혀 있는가?
2. 이미 있는 `secrets.FIREBASE_SERVICE_ACCOUNT`에 Hosting 배포 권한이 있는가? 없으면 무엇이 필요한가?
3. 새 도메인이 reCAPTCHA 승인 목록에 실제로 반영됐는지 어떻게 증명하는가?

## 결과

**1. 경로 접두 — 0건.** 여섯 가지 방법으로 확인했다: 문자열 전수 grep, 빌드 base 설정
(`vite.config.ts`가 `VITE_BASE_PATH`로만 정함), 라우터 부재, 절대경로 문자열(`index.html`의 Vite
개발 진입점 하나뿐이고 빌드 시 치환됨), 매니페스트 상대경로(`./`), 서비스워커 부재. **코드 수정
없이 워크플로 env 두 줄 교체로 끝났다.**

**2. 서비스 계정 — 권한 있었다.** 규칙 배포에 쓰던 계정을 그대로 재사용해 Hosting 배포가 성공했다.
새 자격증명을 만들지 않았다.

**3. reCAPTCHA 등록 증명 — 실동작으로 확인했다.** 새 도메인에서 `?pairing=1`에 여섯 자리를 제출해
**"코드를 찾지 못했어요"**(정상 invalid 응답)가 나오고 4xx/5xx가 0건이었다. reCAPTCHA의 `출처 확인`이
켜져 있으므로, 이 응답은 익명 로그인 → App Check 토큰 발급 → Firestore 조회가 전부 통과했다는 뜻이다.

**그 밖에 확인한 것**: 보안 헤더 5종이 실제 응답에 존재, 콘솔 오류 0건, CSP 위반 0건, 골든패스
1→5단계 정상, 처리방침 링크 정상, **Pages 화면과 픽셀 차이 0**(데스크톱 2,073,600px / 모바일
329,160px, 애니메이션 정지 후 대조), SPA 폴백·`privacy.html` 200, 옛 주소 404.

**이전 중 발견해 고친 결함 1건**: 첫 배포 뒤 헤더를 재보니 루트(`/`)에 `Cache-Control: max-age=3600`이
붙어 있었다. `**/*.html` 패턴이 `/` 요청에 매칭되지 않아 Firebase 기본값이 걸린 것이고, 그대로 두면
배포해도 최대 1시간 동안 재방문자가 옛 HTML을 받는다. 전역 `**`을 `no-cache`로 두고 `/assets/**`만
immutable로 덮도록 고쳐 재배포했다.

**검증 수단의 한계**: Claude in Chrome 확장이 연결되지 않아 Playwright 실제 Chromium으로 검증했다.
헤드리스에서는 reCAPTCHA v3가 자동화를 차단해 App Check가 403으로 실패하는데, **같은 403이 당시
정상 운영 중이던 Pages에서도 동일하게 재현**되어 이전 탓이 아님을 확인했고 헤드 모드에서는 양쪽 다
정상이었다.
